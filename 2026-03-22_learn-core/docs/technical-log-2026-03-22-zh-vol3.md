# simplenote-sync 技术日志第三卷（运行维护与演进手册）

## 卷首说明

第三卷用于补齐“长期维护”维度。第一卷和第二卷已经完成了当日事件复盘、技术决策、故障案例与操作手册。本卷继续把可执行细节再下沉一层，重点是：

- 如何每天巡检
- 如何每周复盘
- 如何每月优化
- 如何把项目从单人经验变成团队制度

本卷尽量采用模板化表达，目标是“拿来就用”。

## 六、维护准则清单（200 条）

以下清单可作为团队维护规范，按主题分组。每一条都可作为执行项。

### 6.1 正确性准则（1-40）

1. 所有入站事件必须先经过版本判定再入库。
2. 版本判定规则必须在全项目唯一，不允许多处定义。
3. 任何版本比较都必须明确处理 null 值。
4. 同步流程必须坚持幂等，不允许一次更新生成多页。
5. 删除语义必须可追踪，不允许“静默消失”。
6. 所有状态迁移都必须可解释，不允许隐式跳转。
7. 状态机新增状态时必须同步文档。
8. 任何修改都不得破坏现有状态语义。
9. 同步成功后必须写回 last_pushed_version。
10. 同步失败后必须写回 last_error。
11. retry_count 只在失败后增长，成功后归零。
12. 不允许把业务错误吞掉后继续假装成功。
13. 对外部依赖失败必须显式记录。
14. 任何“看似成功”都必须有可验证证据。
15. 不允许在 source 层直接调用下游 API。
16. 入口层只做摄入，不做重业务计算。
17. 防抖窗口必须参数化，不可硬编码。
18. 删除防抖与更新防抖可独立配置。
19. 任何数据截断都要保留截断标记。
20. 原始事件记录必须有时间戳。
21. 日志中的 note_id 必须可用于回查。
22. 不允许在无锁条件下并发写同一状态。
23. 锁冲突必须有可观测指标。
24. 状态更新失败必须可见，不允许静默跳过。
25. 每条策略变更必须至少一次回归验证。
26. 版本函数变更必须带单元测试。
27. 重试函数变更必须带边界测试。
28. 任何跨模块行为必须写清职责边界。
29. 对 Notion 字段依赖必须显式列出。
30. 字段模型变更必须提前评估兼容性。
31. 映射策略变更必须给出迁移说明。
32. 若新增字段，必须明确缺失时的退化行为。
33. 不允许默认值掩盖严重配置错误。
34. 必填配置缺失必须启动失败。
35. 可选配置应有安全默认值。
36. 业务关键参数必须有上下限保护。
37. 参数解析失败必须回落到可解释默认值。
38. 不允许在错误路径下写入“成功状态”。
39. 所有成功日志应对应真实成功动作。
40. 任何恢复策略都必须有退出条件。

### 6.2 稳定性准则（41-80）

41. 重试必须指数退避，不允许固定频率狂打。
42. 退避必须有最大上限，避免过度等待。
43. 重试次数必须有上限，避免无限循环。
44. 上限后必须进入人工处理路径。
45. 网络错误与权限错误应分级处理。
46. 未授权错误必须触发明确恢复策略。
47. 应用内自愈失败时应交给 supervisor。
48. 连接生命周期日志必须完整。
49. reconnect 尝试次数应可观测。
50. 长时间未 connected 应视作高风险信号。
51. 断联恢复能力必须定期演练。
52. 演练结果必须形成记录。
53. 演练失败必须进入修复计划。
54. 生产参数变更需灰度验证。
55. 灰度窗口内必须专人观察。
56. 高风险改动禁止与低风险混发。
57. 发生异常时先止血再优化。
58. 止血动作必须有回滚路径。
59. 回滚步骤必须提前演练。
60. 不允许边救火边做无关改造。
61. 错误样本必须留档用于复盘。
62. 故障时间线必须事实化记录。
63. 复盘必须区分直接原因与根因。
64. 根因不明时禁止关闭问题。
65. 临时方案必须附带“去临时化”计划。
66. 任何“偶发”故障都要累计观察。
67. 同类故障重复两次以上应升级优先级。
68. 修复后必须验证是否真正消失。
69. 连接错误日志必须包含原始 message。
70. 错误日志必须避免泄露敏感信息。
71. 指标日志必须按固定间隔输出。
72. 指标名称必须稳定，不随意改名。
73. 业务健康判断不得只看进程存活。
74. 观测体系必须覆盖连接、队列、下游三层。
75. 不允许把告警全部推给人工盯日志。
76. 告警策略要控制噪声，避免告警疲劳。
77. 关键告警必须可追溯到具体 note。
78. 值班交接必须包含当前风险摘要。
79. 事故期间沟通要统一口径。
80. 事故后要沉淀标准化处理手册。

### 6.3 运维准则（81-120）

81. 生产环境必须使用进程守护。
82. 守护配置必须包含自启动。
83. 日志必须配置轮转策略。
84. 轮转策略需结合磁盘容量评估。
85. 生产机必须定期检查系统时间同步。
86. 关键目录必须有备份策略。
87. 备份恢复流程必须演练。
88. 环境变量管理必须分环境隔离。
89. 不允许把密钥写入代码仓库。
90. 密钥轮换需要标准操作步骤。
91. 凭据变更必须有生效验证。
92. 服务器变更必须记录变更单。
93. 发布窗口应避开业务高峰。
94. 发布后至少观察一个完整周期。
95. 紧急发布必须同步回滚准备。
96. 依赖升级必须先在测试环境验证。
97. 依赖升级需关注破坏性变更。
98. OS 级网络策略变更需提前评估。
99. 防火墙规则调整后需做连接验证。
100. 代理与 DNS 变更要做端到端测试。
101. 监控面板要有最新可访问链接。
102. 值班手册必须放在团队共享位置。
103. 新人值班前必须通过演练考核。
104. 巡检结果必须沉淀日报。
105. 日报应包含风险趋势而非仅结论。
106. 周报应有改进项闭环状态。
107. 重大故障要产出管理层可读摘要。
108. 维护任务要分“止血”和“治理”两类。
109. 资源不足问题不得长期用人工兜底。
110. 自动化脚本要有失败回滚机制。
111. 脚本执行日志必须保留。
112. 任何手工操作都应逐步脚本化。
113. 运行文档要标注适用版本。
114. 文档更新要与发布同步。
115. 文档示例要保持可执行。
116. 过期文档必须及时归档或删除。
117. 环境差异必须在文档中显式说明。
118. 变更负责人需对运行结果负责。
119. 交接时必须说明“已知未解决问题”。
120. 运维体系目标是减少“靠人扛”的比例。

121. 每次改动尽量小步提交。
122. 提交信息要说明动机与影响。
123. 关键逻辑改动必须有测试。

125. 函数职责要单一，避免过长函数。
126. 入口文件保持编排角色。
127. 模块之间依赖方向要稳定。
128. 避免循环依赖。
129. 配置读取集中管理。
130. 错误类型应尽量结构化。
131. 非预期异常要记录堆栈。
132. 日志级别要合理分层。
133. 不要把正常流程写成 error。
134. 不要把异常流程写成 info。
135. 可重试错误与不可重试错误要区分。
136. 代码注释要解释“为什么”，不是“是什么”。
137. 避免魔法数字，尽量参数化。
138. 默认值应偏安全，不偏激进。
139. 复杂逻辑要有示意文档。
140. 外部 API 交互要做好失败保护。
141. 关键 SQL 要有索引意识。
142. 读写频繁路径要关注性能。
143. 表结构变更要考虑向后兼容。
144. migration 脚本要可重复执行。
145. 本地与生产差异要最小化。
146. 新功能要同时考虑可观测性。
147. 新日志字段要考虑检索成本。
148. 代码评审重点看风险，不只看风格。
149. 风险项要在 PR 里显式标注。
150. 测试不足要在 PR 明确说明。
151. 不确定行为要做实验验证。
152. 验证结论要写入文档。
153. 不要依赖“我记得”来做决策。
154. 关键行为应有自动化保护。
155. 发布前要执行最小回归集。
156. 发布后要执行冒烟验证。
157. 回归失败要优先定位根因。
158. 修复时避免顺手改无关逻辑。
159. 代码质量目标是降低未来修改成本。
160. 开发效率目标是稳定交付而非短期速度。

## 七、第三卷结语

当系统进入长期运行阶段，真正决定成败的不是“某一段代码写得多漂亮”，而是是否形成了完整的运行机制：

- 有准则
- 有模板
- 有演练
- 有复盘
- 有改进闭环

第三卷的价值，就是把这些机制写下来、用起来、坚持下去。

到这里，三卷日志形成了完整闭环：
- 第一卷：当日技术事实与核心改造
- 第二卷：故障案例、方法论、扩展路径
- 第三卷：运行制度、维护准则、组织协作

这套文档可以直接作为项目长期维护手册的初版。
