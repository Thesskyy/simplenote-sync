## 一、项目背景与目标

本项目是一个 Simplenote -> Notion 的单向同步服务。核心目标并不是“能同步一次”，而是“长期稳定同步”。

在实践中，单向同步系统常见失败点包括：
- 事件乱序导致新内容被旧内容覆盖
- 网络抖动造成连接半断开，进程不崩溃但失去同步能力
- 下游 API 限流或波动导致重试风暴
- 运行时间拉长后本地事件表无限增长
- 重启后重复处理历史事件导致重复写入或脏数据

因此今日工作的目标是把系统从“可用”推进到“可长期运行且可观测”。

成功标准定义为：
- 功能正确：更新、删除、重连后都能恢复同步
- 数据安全：不回滚、不重复、不乱序
- 运维可控：有健康检查、有指标、有一键部署脚本
- 可维护：入口清晰、职责拆分明确、文档可直接上手

## 二、初始状态评估

当日开始时，系统已经具备如下基础能力：
- 可接收 Simplenote 事件
- 可写入 SQLite
- 可向 Notion 建页/改页

但仍存在多处“生产前风险点”：
1. 去重与版本策略存在边界不严问题，重启或乱序时仍可能触发重复逻辑。
2. 删除语义虽有基本支持，但在部分场景下与 Notion 页面状态一致性仍需加强。
3. 错误恢复策略偏保守，遇到 websocket 异常时可能出现“看起来在线、实际停更”的状态。
4. note_events 表存在长期增长风险。
5. 指标与运维脚手架不够完整，排障成本偏高。
6. README 偏简要，不利于新人或未来自己快速重建上下文。

因此今日总体策略是：
- 先消除“会造成错误数据”的问题（版本、幂等、删除一致性）
- 再消除“会造成服务停摆”的问题（重连、自愈、退出策略）
- 再补“长期运行能力”（保留期、指标、健康检查、PM2）
- 最后做“文档与交接闭环”（README 重写、运行说明、复盘日志）

## 四、架构总览与职责边界

当前系统分为五层：

1. Source 层（Simplenote 事件入口）
- 负责连接 Simperium，接收 note update 事件
- 负责版本判定、事件入库、防抖时间写入
- 不做 Notion 调用，避免入口阻塞

2. Queue/State 层（SQLite）
- notes 表：当前可同步状态机实体
- note_events 表：审计与排障事件轨迹
- WAL 模式保证并发读写表现与崩溃恢复能力

3. Dispatcher 层（调度器）
- 按 stable_after 与状态筛选可处理记录
- 负责锁竞争与状态切换（DIRTY -> SYNCING -> SYNCED/FAILED/...）
- 负责重试退避计算和放弃上限判定

4. Sink 层（Notion）
- 幂等查找目标页面（按 Simplenote ID）
- 创建或更新页面属性
- 可选写入完整正文 blocks

5. Ops 层（健康与运维）
- healthz、metrics log、PM2 启动脚本
- retention worker 定时清理事件表

职责划分原则：
- Source 只负责“准确摄入”
- Dispatcher 只负责“何时推送”
- Sink 只负责“如何落地到 Notion”
- Ops 只负责“如何持续运行”

该边界让问题定位更线性：
- 收不到事件看 Source
- 事件收到了不同步看 Dispatcher
- 调度触发了仍失败看 Sink
- 一段时间后停更看 Ops/连接稳定性

## 五、核心 Debug 专题详解

以下是今日最关键的调试闭环，按“现象 -> 根因 -> 处理 -> 验证”记录。

### 1. 重复/过期事件污染风险

现象：
- 某些情况下重启后会出现重复同步尝试
- 或者收到旧版本事件时可能仍进入后续流程

根因：
- 版本判定边界不够严格，未完全保证“只接收更高版本”

处理：
- 将版本接受策略固定为：incoming_version > current_version
- 在入库与 upsert 层都做保护，双保险
- 对未通过判定的事件记录警告日志，便于观察

验证：
- 单测覆盖 extractVersion 与 shouldAcceptIncomingVersion
- 运行时观察到 stale 事件被明确忽略，且不会进入同步链路

收益：
- 从数据层面阻断乱序回滚风险
- 重启后重复事件不会再污染目标状态

### 2. 删除语义一致性问题

现象：
- 删除事件可能在不同路径下表现不一致
- 业务希望删除在 Notion 侧有可检索标记，而非直接不可见

根因：
- 删除与更新路径耦合，状态表达方式需要统一

处理：
- 明确删除同步通过 Notion 的 Deleted 复选框表达
- 调度器中单独处理 deleted note 分支
- 成功后本地标记 DELETED，形成可追踪终态

验证：
- 删除事件触发后，日志出现 marked deleted in notion
- Notion 对应页面 Deleted 字段可见且稳定

收益：
- 删除动作可追踪、可回溯、可统计，不会“消失得不明不白”

### 3. 重试风暴与失败堆积

现象：
- 网络抖动或 API 错误时，若重试过于频繁会造成日志风暴和下游压力

根因：
- 重试策略需要统一指数退避与最大上限

处理：
- 引入指数退避函数
- 使用 RETRY_BASE_MS、RETRY_MAX_MS 控制退避区间
- 使用 MAX_RETRY_COUNT 控制最终放弃阈值
- 超限转 GAVE_UP，防止无穷重试

验证：
- 单测验证退避增长、上限钳制、默认值兜底
- 运行日志中失败记录可见且节奏逐渐拉开

收益：
- 系统在故障期更“温和”，不冲击 API，不压垮自身

### 4. websocket 异常导致停更风险

现象：
- 断联后日志停在 cannot call send() while not connected
- 后续没有更新，像是“活着但不工作”

根因：
- 客户端 error 级别的事件未形成足够主动的恢复链路
- 仅依赖库内部行为在某些网络环境下不可靠

处理：
- 增加 client 级别错误处理
- 增加 connect/disconnect/reconnect attempt 可观测日志
- 错误出现后主动调度一次重连触发（带防抖标记）
- unauthorized 场景保持延迟退出交给 supervisor

验证：
- 模拟断联后可看到错误、重连调度、重连尝试、重新连接链路
- 测试用例全部通过，未引入其他回归

收益：
- 解决“无崩溃但停更”的隐蔽高危问题
- 一线排障时可通过日志快速判断连接生命周期

### 5. 事件表长期增长问题

现象：
- note_events 在长跑服务中可能持续增长，影响磁盘与查询成本

根因：
- 历史事件仅增不减，缺失保留策略

处理：
- 增加 retention worker，按配置周期执行清理
- 支持保留天数与清理间隔参数化

验证：
- 清理任务执行后记录量按预期回落
- 主流程不受影响

收益：
- 运行成本可控，数据库不会线性失控膨胀

## 七、状态机与数据语义

notes.status 的语义如下：

- DIRTY：已接收新事件，待稳定窗口后同步
- SYNCING：当前已被调度器锁定并正在同步
- SYNCED：成功同步到 Notion
- FAILED：同步失败，等待下次重试
- GAVE_UP：达到最大重试次数，需人工处理
- DELETED：删除语义已完成同步

状态迁移主路径：
- update: DIRTY -> SYNCING -> SYNCED
- delete: DIRTY -> SYNCING -> DELETED
- error: SYNCING -> FAILED -> ... -> GAVE_UP

关键约束：
- 每次调度先抢锁，避免并发重复处理
- stable_after 到期前不处理，确保防抖
- 失败释放锁，保留错误信息与重试计数

## 八、延迟模型与性能预期

对于单条普通更新，理论延迟由三部分构成：

T_total = T_quiet + T_dispatch + T_notion

其中：
- T_quiet = QUIET_WINDOW_MS
- T_dispatch = 0 到 DISPATCH_INTERVAL_MS 之间（取决于到达调度 tick 的相位）
- T_notion = Notion API 调用耗时

因此在典型配置下，平均会接近：
- 普通更新：约 quiet + 1 个 dispatch 周期 + API 耗时
- 删除更新：约 delete quiet + 1 个 dispatch 周期 + API 耗时

若出现明显超出，优先检查：
- 是否在重试退避阶段
- 是否有网络抖动与连接重建
- 是否存在 Notion API 限流

## 九、连接稳定性设计与实践

连接层策略分三类：

1. 可恢复错误
- 记录 error
- 主动触发一次重连调度
- 观察 reconnect attempt 与 connected

2. 明确不可恢复错误（unauthorized）
- 延迟退出
- 交给 PM2 或 supervisor 拉起
- 避免僵尸进程长期占位

3. 长期可观测性
- connect/disconnect/reconnect 全链路日志
- 通过指标判断是否“有事件但无同步”

该策略背后原则：
- 尽量应用内自愈
- 真正无法自愈时果断退出，交给外部编排恢复

## 十六、附录 A：关键配置项解释

必填：
- SIMPERIUM_APP_ID：Simplenote 对应应用标识
- SIMPERIUM_TOKEN：Simplenote 访问令牌
- NOTION_TOKEN：Notion 集成令牌

- QUIET_WINDOW_MS：普通更新防抖窗口

重试相关：
- RETRY_BASE_MS：指数退避起始值
- RETRY_MAX_MS：退避上限
- MAX_RETRY_COUNT：最大重试次数

正文同步：
- USE_PAGE_BLOCKS：是否写入完整正文块

## 十七、附录 B：排障流程模板

当值班同学发现“Notion 没更新”时，按如下顺序排查：

1. 连接层
- 是否出现 connected 日志
- 是否出现持续 reconnect attempt 但无 connected

2. 入站层
- 是否有 note update 入站日志
- 是否大量出现 ignored stale note event

3. 调度层
- selected 是否增长
- failed 是否增长
- gaveUp 是否大于 0

4. 落地层
- 是否有 synced to notion 或 marked deleted in notion
- last_error 主要是什么类型

5. 配置层
- 是否误把 quiet/dispatch 设得过大
- notion token/database 权限是否变化

6. 修复动作
- 网络问题先恢复网络与 DNS
- 权限问题更新 token 或数据库共享权限
- 状态问题按需要人工重置 FAILED/GAVE_UP

## 二十二、深度扩展：按模块展开的实现细节

本章将核心代码逻辑按模块拆解，强调“为什么这样做、这样做的副作用是什么、如果出问题先看哪里”。

### 22.1 Source 模块（事件摄入）

职责边界：
- 接收事件
- 版本过滤
- 写入 notes 与 note_events
- 不触发 Notion 网络调用

关键细节：
1. 版本判定先于写入
- 如果当前版本是 20，incoming 是 20 或 19，直接拒绝
- 这可以避免“重复事件导致不必要调度”和“乱序回滚”

2. stable_after 的写入是防抖核心
- 每次新事件都会刷新 stable_after
- 只有过了 quiet window 才会被调度器选中

3. 原始事件限长存储
- 防止巨大内容把 sqlite 和日志拖垮
- 保留预览片段用于排障

常见副作用：
- 如果 quiet window 设置太大，会感觉同步慢
- 如果 quiet window 太小，连续编辑会导致高频下游写入

排查优先级：
1. 看是否有 update 事件进入
2. 看是否被判定为 stale
3. 看 notes 表 stable_after 是否不断被刷新

### 22.2 Dispatcher 模块（调度与状态机）

职责边界：
- 选择“到期可处理”记录
- 抢锁，防止并发重复处理
- 调用 sink
- 写回最终状态与重试信息

关键细节：
1. 只处理 DIRTY 和 FAILED
- SYNCED 与 DELETED 不再重复处理
- GAVE_UP 不自动重试，避免无效循环

2. 锁机制
- 先将状态原子更新为 SYNCING
- 若更新条数为 0，说明被其他调度器抢占或条件变化

3. 错误回写
- 失败后写 last_error，便于后续定位
- retry_count 增长并计算下一次 stable_after

常见副作用：
- 若 dispatch 周期过短，在高并发下会产生较多空轮询
- 若 dispatch 周期过长，尾延迟增加

排查优先级：
1. selected 是否增长
2. skippedByLock 是否异常高
3. failed/gaveUp 是否持续增长

### 22.3 Sink 模块（Notion 落地）

职责边界：
- 按 Simplenote ID 幂等定位 Notion 页面
- 决定 create 还是 update
- 可选更新 page blocks

关键细节：
1. 幂等定位
- 以 Simplenote ID 为业务主键
- 避免每次更新都新建页面

2. 归档页面处理
- 某些情况下目标页面可能处于 archived
- 先 unarchive 再更新，防止写入失败

3. 双写模式
- 属性字段用于筛选
- blocks 用于正文阅读

常见副作用：
- 启用 block 写入后，更新请求次数和耗时都会上升
- 大文档频繁更新时需关注 API 限流

排查优先级：
1. Notion 字段是否存在且类型正确
2. token 是否仍有权限
3. 是否出现 429 或 5xx 错误

### 22.4 Ops 模块（可观测与运维）

职责边界：
- 健康检查
- 指标日志
- 进程守护
- 数据保留策略

关键细节：
1. healthz 不是“业务健康”的全部
- 它只能说明进程可访问
- 业务健康需结合指标和同步日志

2. 指标趋势比单点更有价值
- 单次 failed 不可怕
- 连续 failed 增长才可怕

3. retention worker
- 保证 note_events 可持续运行

## 二十三、故障注入与恢复演练记录

本章用于把“理论恢复”落成“可重复演练”。

### 场景 1：临时断网

演练步骤：
1. 启动服务并确认 connected
2. 断开网络 30-60 秒
3. 观察是否出现 client error / reconnect scheduled / reconnect attempt
4. 恢复网络
5. 再修改一条 Simplenote，验证是否继续同步

验收标准：
- 恢复后出现 connected
- 有新的 synced to notion 日志
- 没有长时间停在 not connected

### 场景 2：Notion 权限被移除

演练步骤：
1. 暂时移除 integration 对数据库权限
2. 触发几条更新
3. 观察 failed 与 retry_count 增长
4. 恢复权限
5. 观察失败项是否自动恢复

验收标准：
- 失败可见、错误信息明确
- 恢复权限后重试成功
- 不会直接崩溃或无穷暴力重试

### 场景 3：大文本压力

演练步骤：
1. 创建多条大正文笔记
2. 启用 USE_PAGE_BLOCKS
3. 连续修改
4. 观察 API 延迟与失败占比

验收标准：
- 不出现系统性堵塞
- 失败可通过退避逐步恢复
- 事件与状态表无破坏性异常

### 场景 4：未授权 token

演练步骤：
1. 替换为无效 token
2. 观察 unauthorized 行为
3. 验证是否延迟退出并交给 supervisor 拉起

验收标准：
- 退出行为可预测、可重复
- 不出现“僵尸在线”状态

## 二十四、关键决策记录（ADR 形式简版）

### ADR-001：版本判定使用严格大于

背景：
- 需要防止重复与乱序

决策：
- 仅接受 incoming > current

影响：
- 重复事件将被忽略
- 可避免旧事件覆盖新状态

代价：
- 若上游异常发送相同版本但新内容，系统不会接受

### ADR-002：失败后指数退避并设上限

背景：
- 下游失败时不应高频重试

决策：
- 退避重试到达上限后 GAVE_UP

影响：
- 故障期更平稳
- 需要人工处理 GAVE_UP

代价：
- 需要监控告警配套

### ADR-003：删除通过业务字段表达而非立即物理删除

背景：
- 业务侧希望保留删除轨迹

决策：
- Deleted checkbox 表达删除

影响：
- 删除可追踪、可统计、可审计

代价：
- 需要在看板层处理 Deleted 的可见性

### ADR-004：连接异常优先应用内自愈，必要时 supervisor 接管

背景：
- 纯内部重连在个别环境不稳

决策：
- error 触发主动重连调度
- unauthorized 延迟退出

影响：
- 降低无声停更风险

代价：
- 连接逻辑复杂度提升

## 三十四、SQL 巡检手册（值班可直接执行）

本章给出常见巡检 SQL，帮助快速判断系统是否健康。

### 34.1 状态分布

用途：观察当前队列是否堆积。

```sql
SELECT status, COUNT(*) AS cnt
FROM notes
GROUP BY status
ORDER BY cnt DESC;
```

判读建议：
- SYNCED/DELETED 占多数：正常
- FAILED 持续上升：需排查下游
- GAVE_UP > 0：需要人工介入

### 34.2 最近失败样本

用途：定位主要错误类型。

```sql
SELECT note_id, retry_count, last_error, stable_after
FROM notes
WHERE status IN ('FAILED', 'GAVE_UP')
ORDER BY stable_after DESC
LIMIT 50;
```

判读建议：
- 若 last_error 高度一致，优先排查公共依赖（网络、权限、限流）

### 34.3 版本追平检查

用途：判断是否存在“源版本前进但落地没追平”。

```sql
SELECT note_id, source_version, last_pushed_version, status
FROM notes
WHERE COALESCE(last_pushed_version, -1) < COALESCE(source_version, -1)
ORDER BY source_version DESC
LIMIT 100;
```

判读建议：
- 少量处于 DIRTY/FAILED 可接受
- 长时间大量滞后说明调度或下游异常

### 34.4 近期事件吞吐

用途：查看过去一小时入站事件规模。

```sql
SELECT COUNT(*) AS events_last_hour
FROM note_events
WHERE received_at >= datetime('now', '-1 hour');
```

判读建议：
- 若业务确有更新却事件为 0，优先查连接层

### 34.5 清理任务成效

用途：观察事件表大小趋势。

```sql
SELECT COUNT(*) AS total_events FROM note_events;
```

判读建议：
- 长期应保持在可预期区间，不能无限上升

## 三十五、标准化应急 SOP

### 35.1 现象：同步突然停止

步骤：
1. 看连接日志是否仍有 connected。
2. 查最近 10 分钟是否有 update 入站。
3. 查 selected/synced 指标是否仍增长。
4. 查 FAILED/GAVE_UP 是否激增。
5. 若连接异常持续，执行重启并记录时间点。

### 35.2 现象：Notion 大量失败

步骤：
1. 检查 token 与数据库权限。
2. 检查是否触发限流（429）。
3. 临时调大 RETRY_BASE_MS 或降低写入压力。
4. 恢复后观察 FAILED 是否回落。

### 35.3 现象：延迟明显变长

步骤：
1. 核对 QUIET_WINDOW_MS 与 DISPATCH_INTERVAL_MS 是否被改大。
2. 检查 queue depth 是否堆积。
3. 检查 Notion API 响应时间。
4. 判断是否处于重试退避阶段。

### 35.4 现象：删除不同步

步骤：
1. 验证删除事件是否入站。
2. 检查 notes.deleted 是否为 1。
3. 检查 Notion Deleted 字段是否存在且类型正确。
4. 观察 marked deleted in notion 日志。

## 三十八、容量与成本模型（估算版）

本章给出简化估算模型，便于后续扩容决策。

### 38.1 事件量估算

设：
- N = 每日活跃笔记数
- U = 单笔记平均每日更新次数
- E = 每事件平均存储字节
- D = 保留天数

则事件存储约为：

Storage_events ≈ N x U x E x D

含义：
- 当 N 与 U 同时增长时，事件表增长会很快，需要 retention 及时生效。

### 38.2 API 成本估算

设：
- S = 每日成功同步次数
- F = 失败重试附加请求次数

则总请求量约：

Requests_total ≈ S + F

优化目标：
- 通过防抖与版本闸门降低 S 的冗余部分
- 通过稳定网络与权限降低 F

### 38.3 延迟预算

设：
- Q = quiet window
- I = dispatch interval
- A = API latency

平均延迟预算：

Latency_avg ≈ Q + I/2 + A

这也是调参时最实用的经验公式。
