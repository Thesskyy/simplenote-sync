## 一、长期运行的核心矛盾

同步系统在真实环境里长期运行时，矛盾主要集中在三个方面：

1. 正确性与实时性的矛盾
- 更短的 quiet window 追求“快”，但会增加抖动写入
- 更长的 quiet window 追求“稳”，但用户感知延迟上升

2. 自愈与可控性的矛盾
- 应用内自动重连能提升可用性
- 但过度自愈可能隐藏底层问题，延迟报警

3. 日志充分性与成本的矛盾
- 日志太少无法定位
- 日志太多会淹没有效信号并增加成本

解决这些矛盾没有一劳永逸的参数，只有“可观测 + 可调优 + 有边界”。

## 二、参数调优方法论（实战版）

本章给出可直接执行的调优流程。

### 2.1 第一轮：先确定业务期望

先回答两个问题：
1. 你能接受的典型同步延迟是多少？
2. 你每日更新密度是“低频”还是“高频 burst”？

建议分层：
- 轻量个人使用：延迟 5-20 秒通常可接受
- 高密度写作：优先稳态，避免高频 API 抖动

### 2.2 第二轮：确定初始参数

推荐起步值：
- QUIET_WINDOW_MS：3000-8000
- DELETE_QUIET_WINDOW_MS：3000-5000
- DISPATCH_INTERVAL_MS：1000-3000
- RETRY_BASE_MS：2000
- RETRY_MAX_MS：300000
- MAX_RETRY_COUNT：8

### 2.3 第三轮：跑 24 小时观察

重点看四个趋势：
1. failed 增速
2. gaveUp 是否出现
3. 平均同步延迟
4. 连接重建频率

调优规则：
- failed 高：提高 quiet 或增加重试基数
- 延迟高：降低 quiet 或降低 dispatch interval
- API 压力高：提高 quiet 并观察

### 2.4 第四轮：形成基线

当指标稳定后，冻结参数，标记为 baseline。
后续每次改参数必须记录：
- 改前值
- 改后值
- 改动理由
- 24h 结果

## 三、故障案例库（细化）

本节按“告警信号 -> 判断 -> 动作 -> 预期结果”给出案例。

### 案例 01：日志有 connected，但没有 synced

告警信号：
- 连接看起来正常
- 但业务方反馈 Notion 长时间无更新

判断路径：
1. 查是否有 update 入站
2. 查 notes 是否大量停在 DIRTY
3. 查 stable_after 是否未来时间
4. 查 dispatch interval 是否过大

动作：
- 若 stable_after 被持续刷新，说明同笔记在高频编辑，属于防抖行为
- 若 selected 长期为 0，检查查询条件和系统时间

预期结果：
- 调整参数后同步恢复，DIRTY 回落

### 案例 02：failed 逐步增长但最终可恢复

告警信号：
- failed 在某个时间窗增长
- 但随后回落

判断：
- 多为短时网络或下游波动

动作：
- 保持观测，不立即人工干预
- 重点确认 gaveUp 未增长

预期结果：
- 退避重试自动收敛

### 案例 03：gaveUp 出现且持续上升

告警信号：
- gaveUp > 0
- 且每小时新增

判断：
- 系统性故障，不是瞬时抖动

动作：
1. 抽样查看 last_error
2. 优先排查 token 权限、字段模型、网络白名单
3. 修复后对 GAVE_UP 做人工重放策略

预期结果：
- 新增 gaveUp 归零
- 历史问题项逐步清空

### 案例 04：更新正常，删除不同步

告警信号：
- 普通编辑可同步
- 删除行为在 Notion 看不到

判断：
- 删除字段、映射逻辑、过滤视图三者之一异常

动作：
- 检查 Deleted 字段类型是否 checkbox
- 检查调度删除分支日志
- 检查 Notion 视图是否过滤了 Deleted=true

预期结果：
- 删除动作可见且可审计

### 案例 05：断网恢复后出现长时间静默

告警信号：
- 出现 not connected 错误
- 后续迟迟无 connected

判断：
- 重连链路可能卡住

动作：
- 观察是否有 reconnect attempt
- 若无恢复，手动重启并记录时间窗
- 对应时间窗查看网络与 DNS

预期结果：
- 恢复后有新的 update 和 synced

### 案例 06：Notion 字段突然报错

告警信号：
- last_error 出现 property not found / validation failed

判断：
- 目标数据库字段被改名、删除或类型变更

动作：
- 恢复字段名称和类型
- 建议增加启动时字段自检（未来项）

预期结果：
- 校正后重试恢复

### 案例 07：系统重启后短时负载升高

告警信号：
- 刚重启时 selected 增高

判断：
- 重启期间积压任务被调度，属于正常行为

动作：
- 观察 10-30 分钟是否回落
- 若不回落，进一步查 failed

预期结果：
- 队列被逐步清空，恢复稳态

### 案例 08：Content Preview 正常但正文不完整

告警信号：
- 数据库列表看起来对
- 打开页面正文缺失或旧内容

判断：
- block 替换流程异常

动作：
- 检查 USE_PAGE_BLOCKS 是否开启
- 检查更新路径是否执行 block 替换

预期结果：
- 页面正文与源笔记一致

### 案例 09：日志量突然暴涨

告警信号：
- 每分钟日志条数显著增加

判断：
- 可能是 sourceEventInfoEvery 过小或异常重试频发

动作：
- 调高采样间隔
- 同时定位 failed 的根因

预期结果：
- 日志恢复到可读水平

### 案例 10：数据库体积增长异常

告警信号：
- 文件体积增长快于预期

判断：
- retention 未生效或事件量突增

动作：
- 核查 retention 配置
- 检查 purge worker 是否在运行

预期结果：
- 体积增长曲线回归正常

## 四、值班问答（FAQ 长版）

### Q1：为什么要等 quiet window，不直接实时写 Notion？

A：
直接实时写在连续编辑时会造成大量冗余请求，既增加成本也更容易触发限流。quiet window 的核心价值是把“编辑抖动”合并成“稳定快照”。

### Q2：为什么失败后不一直重试，非要 GAVE_UP？

A：
无限重试会造成资源浪费和噪声放大。GAVE_UP 是工程边界，目的是把“机器无法恢复的问题”显式交给人处理。

### Q3：版本判定为什么是严格大于？

A：
因为相等通常意味着重复事件，小于通常意味着乱序或过期。严格大于是最稳妥的防回滚策略。

### Q4：为什么删除不做物理删除？

A：
业务层面通常需要审计和可追踪性。用 Deleted 字段表达可保留历史并支持过滤。

### Q5：为什么既要应用内自愈又要 PM2？

A：
应用内自愈处理可恢复故障，PM2 处理不可恢复故障。两者分工互补。

### Q6：如何定义“今天系统健康”？

A：
至少满足三条：
1. connected 正常
2. synced 持续增长
3. failed 与 gaveUp 没有异常上升

### Q7：为什么要保留 note_events，不只保 notes？

A：
notes 代表当前状态，note_events 代表过程证据。没有过程证据，很多异常无法追溯。

### Q8：如果用户说“我刚改了，为什么没同步”？

A：
先解释存在 quiet window 与 dispatch interval，再查是否处于连续编辑导致防抖刷新。

### Q9：如何快速判断是连接问题还是下游问题？

A：
- 没有 update 入站：偏连接问题
- 有入站但 failed 激增：偏下游问题

### Q10：为什么要写这么详细的日志文档？

A：
因为同步系统最怕知识只在作者脑中，交接后会快速退化。详细日志是长期稳定的基础设施。

## 五、回滚与补偿策略

### 5.1 什么时候需要回滚

触发条件示例：
- 新版本导致 failed 大幅增长
- 出现大面积错误写入
- 连接恢复能力显著下降

### 5.2 回滚步骤建议

1. 记录当前版本与参数
2. 停止服务
3. 切回上一个稳定版本
4. 启动并观察 15-30 分钟
5. 确认关键指标恢复

### 5.3 数据补偿策略

对于失败或放弃项：
- 按错误类型分批处理
- 修复根因后进行重放
- 重放过程关注限流与重试

## 九、维护者心理模型

为了让维护者快速理解系统，建议采用以下心理模型：

1. 这是一个“状态机驱动的异步系统”，不是请求-响应应用。
2. 任何异常都沿三层定位：连接层 -> 调度层 -> 下游层。
3. 指标看趋势，日志看细节，状态表看事实。
4. 先恢复服务，再做根因分析。
5. 所有修复都要留下可复现证据。

## 十一、从个人项目到可运营服务的跃迁

这一段是本项目今天最核心的工程价值总结。

今天的工作把这条鸿沟补上了：
- 有策略：版本、重试、状态机

- 有观测：指标、日志、健康
- 有治理：保留期、文档、SOP

这就是从“代码完成”到“工程完成”。

## 十二、附录：超细粒度排障问答 60 条

以下问答用于值班场景，尽量覆盖高频问题。

1. 问：为什么 selected=0 但有用户更新反馈？
答：先看是否还在 quiet window，或系统时间偏差导致 stable_after 未到。

2. 问：为什么 selected>0 但 synced 不增长？
答：检查 failed 是否增长、last_error 类型是否一致。

3. 问：为什么 failed 增长但日志不多？
答：可能日志采样较低，建议临时提高故障日志级别。

4. 问：retry_count 清零条件是什么？
答：成功同步后归零。

5. 问：为什么 GAVE_UP 后不自动恢复？
答：设计上避免无限重试，需人工确认根因后处理。

6. 问：删除为什么不直接删 Notion 页面？
答：为了审计与可逆操作，采用字段标记。

7. 问：block 写入失败会不会影响属性写入？
答：按当前实现路径，整体同步失败会进入重试。

8. 问：如何判断是单条脏数据还是系统性故障？
答：抽样 20 条 last_error，若高度同类通常是系统性问题。

9. 问：为什么日志里 stale event 增多？
答：可能是上游重复事件或重连后的历史回放，不一定是故障。

10. 问：如何验证版本闸门生效？
答：观察 stale 日志与状态表是否未被旧版本覆盖。

11. 问：哪些状态需要重点盯？
答：FAILED、GAVE_UP、DIRTY 长时间滞留。

12. 问：DIRTY 很多是否一定异常？
答：不一定，高频编辑期会短时上升，关键看是否能回落。

13. 问：如何定义“回落”？
答：在业务低峰期，DIRTY/FAILED 应明显下降。

14. 问：为什么要记录 source_created_at？
答：保留源数据时间语义，便于下游排序与审计。

15. 问：如果 Notion 字段改名会怎样？
答：同步可能失败，last_error 会出现字段相关错误。

16. 问：如何避免字段被误改？
答：在团队文档中固定字段名并限制编辑权限。

17. 问：为什么要拆 worker？
答：入口简洁可维护，职责分离利于定位与扩展。

18. 问：为什么 healthz 不能代表全部健康？
答：healthz 只说明进程活着，不说明业务在推进。

19. 问：如何定义业务健康？
答：connected 正常 + synced 增长 + failed 可控。

20. 问：如何快速检查连接抖动？
答：统计单位时间 reconnect attempt 次数。

21. 问：是否需要数据库索引？
答：需要，尤其是状态与时间相关查询路径。

22. 问：为什么 note_events 需要 retention？
答：避免无上限增长影响成本与性能。

23. 问：retention 会不会丢证据？
答：会缩短历史窗口，应按审计需求设定保留期。

24. 问：发生故障先看代码还是先看数据？
答：先看数据和日志确定事实，再看代码。

25. 问：如何减少误判？
答：坚持“趋势判断 + 样本抽查 + 时间窗对齐”。

26. 问：quiet window 如何选？
答：看编辑习惯，高频编辑取大一点，低频编辑取小一点。

27. 问：dispatch interval 如何选？
答：看延迟要求与空轮询成本平衡。

28. 问：为什么要记录 lock_owner？
答：便于定位并发争抢来源。

29. 问：skippedByLock 高代表什么？
答：有并发争抢，需确认是否预期。

30. 问：如何确认 Notion 写入是真成功？
答：日志成功 + 目标页面字段实际变更。

31. 问：为何要保留 preview 字段？
答：数据库视图筛选效率高，便于快速检索。

32. 问：为何还要 page blocks？
答：承载完整正文，改善阅读体验。

33. 问：是否可以只用 blocks 不用 preview？
答：可行但会降低数据库级筛选体验。

34. 问：错误信息需要脱敏吗？
答：需要，避免泄露凭据和隐私。

35. 问：日志保留多久合适？
答：按排障与合规需求，至少覆盖最近关键变更窗口。

36. 问：如何定义发布成功？
答：上线后关键场景全部通过且指标稳定。

37. 问：发布后多久观察？
答：建议不少于 30 分钟，关键变更建议 24 小时。

38. 问：如何做灰度？
答：先在低风险环境启用新策略，观察后全量。

39. 问：谁负责参数变更审批？
答：建议由维护负责人统一把关，避免漂移。

40. 问：怎么防止“改了参数忘了记”？
答：强制参数变更记录模板。

41. 问：能不能完全自动恢复不需要人？
答：理论上可提高自动化，但关键凭据和模型错误仍需人工。

42. 问：什么叫可观测？
答：能回答“现在是否健康、为什么不健康、怎么恢复”。

43. 问：什么叫可交接？
答：新人按文档可独立运行、排障、发布。

44. 问：如何评估文档质量？
答：让未参与开发的人按文档执行一次。

45. 问：怎样防止修一个 bug 引入新 bug？
答：小步提交 + 回归测试 + 日志对照验证。

46. 问：为何要把今日过程写成长日志？
答：为未来节省时间，减少重复踩坑。

47. 问：如何判断是否需要重构？
答：当定位成本长期高于改造成本时应重构。

48. 问：当前系统最薄弱点在哪？
答：告警自动化与端到端回归仍需加强。

49. 问：下一步优先级是什么？
答：先告警，再 e2e，再平台化。

50. 问：如何定义“项目完成”？
答：功能稳定 + 运维可控 + 文档可交接。

51. 问：为什么强调趋势而不是单点？
答：单点常有噪声，趋势才能反映系统状态。

52. 问：如何减少 API 压力？
答：合理防抖、减少重复更新、控制重试节奏。

53. 问：如何确认是 token 问题？
答：通常会出现 unauthorized 或权限相关错误。

54. 问：如何确认是字段模型问题？
答：错误多为 validation/property not found。

55. 问：为何要记录 last_pushed_version？
答：用于判断同步是否追平。

56. 问：为什么要避免无限重试？
答：无限重试会掩盖问题并制造更大问题。

57. 问：如何避免部署后立刻回滚？
答：发布前做故障注入演练，验证关键路径。

58. 问：如何减少值班同学学习成本？
答：提供 SOP、FAQ、SQL 巡检模板。

59. 问：项目未来可扩展方向？
答：多源、多目标、告警、可视化、平台化。

60. 问：今天最大的收获？
答：把“能跑”做成“可长期稳定运行”。
